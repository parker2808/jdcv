# Reviewed worker-to-content module mapping

## Problem and boundary

A worker module is not a publishable interview module. The content index needs bilingual metadata, and each entry needs a real key point. For example, the fictional `example-module` cannot be indexed until its role and summary have been reviewed. This pure conversion prepares a document for review; it does not write a file, open a pull request (PR), or publish anything.

The caller supplies reviewed metadata separately from the worker output. No missing translation, key point, date, or reference is fabricated. A worker entry with no key points is rejected even though the version 2 worker contract permits an empty array. The existing `moduleV2Schema` remains unchanged; this is a stricter boundary for content publication, not a new contract version.

## Acceptance checks

1. A fictional raw worker module fails mirrored content rules, while the same module with reviewed metadata maps to a document and matching index row that passes every mirrored rule.
2. Missing metadata, empty key points, malformed references, unlinked requirements, and invalid archive dates fail with a field path; no default content is created.
3. A test-only mirror of the content validator covers index consistency, metadata, archive behavior, entry fields, and reference shapes. The real private validator may also be checked locally against a disposable fictional tree, but private data and repository code never enter this public repository.

Connecting the mapper to the worker publish path and opening content PRs, a regression inside `<private-content-repo>`, knowledge-base autofill, CV approvals, delivery manifest, and lifecycle adapters each remain separate work.
