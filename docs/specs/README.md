# System specifications

The [published portfolio CV source](2026-11-16-portfolio-cv-source.md) keeps the existing owner approval rules while reading public, validated career facts. For example, an Example Labs highlight can supply a cited paragraph but cannot approve an edit.

The [KB autofill worker integration](kb-autofill.md#worker-integration-gap-3) defines the dry-run content client, private plan, and fail-closed module handoff. For example, a fictional pending topic stays pending after it reaches a module entry.

The [worker-to-content mapping](module-content-mapping.md) explains why reviewed bilingual metadata and real key points are required before a fictional worker result can be indexed. It does not publish a module.

These specifications describe how a job description (JD) becomes a tailored curriculum vitae (CV), an interview study module, and downloadable files. They define behavior and checks for later implementation; they do not themselves enable a service. For example, a sample JD for a fictional frontend role can produce a study module without putting the applicant's CV in Git.

The schema is shared by the worker, web view, and Telegram delivery. The worker produces an approval-ready result; embellishment approval precedes export, while knowledge-base (KB) links may wait for a separate content pull request. Phase 1 runs for the owner with a local queue. Phase 2 adds an authenticated web application, database queue, cloud worker, and invited users. Phase 3 opens registration only after legal and abuse checks. Each specification has numbered acceptance criteria and explains how to check them. The [privacy specification](multi-user-and-privacy.md) applies across all phases, not only to public signup.

For the implemented owner-only boundary, read [grounded CV proposals](2026-11-16-grounded-cv-approval.md). It requires a source citation for every CV claim and leaves every proposed line pending; for example, an Example Labs bullet does not enter Word export because a model suggested it.

The [private delivery manifest](delivery-manifest.md) defines the next, opt-in handoff after owner decisions and gated exports. For example, a fictional `example-job` produces a protected manifest only after both approved files exist; the separate private consumer is not implemented here.
